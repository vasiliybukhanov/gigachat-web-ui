# Function calling: модель просит, код исполняет

## Главная мысль

«Модели не исполняют функции самостоятельно» (доки GigaChat). Модель умеет ровно одно:
прочитать описания функций и сгенерировать заявку-JSON «позови такую-то функцию
с такими аргументами». Исполнение — наш код. «Агент» — этот цикл, повторённый N раз.

## Цикл: минимум два запроса к модели

1. Запрос: `messages` + `functions` (описания) + `function_call: "auto"`.
2. Ответ: `finish_reason: "function_call"`, `function_call: {name, arguments}`,
   `content` пустой. Модель НЕ ответила — она ПОПРОСИЛА.
3. Наш код исполняет функцию (без участия модели).
4. В историю добавляются ДВА сообщения: assistant с `function_call` (+ `functions_state_id`)
   и результат с ролью `function` (`name` = имя функции, `content` = строка-JSON).
5. Повторный запрос с выросшей историей → модель отвечает текстом (`finish_reason: "stop"`).

## Описание функции = интерфейс для модели

- `{ name, description, parameters }`; `parameters` — JSON Schema (type/properties/required/enum).
- Модель видит ТОЛЬКО name + description + схему. Код не видит никогда.
- `description` функции решает КОГДА звать: пиши как мини-промпт — что делает, когда вызывать,
  что вернёт. Триггер должен быть про содержимое запроса, а не про «файлы»/«базу».
- `description` параметра решает ЧТО положить: без примера модель перешлёт вопрос целиком.
  Формула из доков: «Местоположение, например, название города» — тип + пример.
- `enum` для фиксированных наборов значений — устраняет целый класс ошибок генерации.
- `required`: не вошедшие в список параметры — опциональные; для них в description пишут
  поведение по умолчанию («по умолчанию 5»).
- `return_parameters` — GigaChat-специфичное расширение (описание формы результата),
  необязательное.
- Схема — интерфейс, а не документация реализации: детали кода туда не пишем.
  Каждое слово схемы — токены КАЖДОГО запроса (функции пересылаются каждый раз).

## Специфика GigaChat (отличия от OpenAI)

- `function_call.arguments` — УЖЕ объект, а не строка (в OpenAI — строка, нужен JSON.parse).
- Результат функции — сообщение с ролью `function` (не `tool`), поля `name` + `content`.
- В ответе есть `functions_state_id` — сохранить и вернуть в истории с assistant-сообщением.
- В стриме имя + аргументы приходят ОДНИМ финальным чанком (в OpenAI докачиваются по кусочкам).
- `finish_reason: "error"` — модель сгенерировала невалидные аргументы.
- Режимы `function_call`: `"auto"` / `"none"` / `{"name": "..."}` — принудительный вызов;
  несуществующее имя в принудительном режиме даёт знакомый плоский 422.

## Практика и грабли

- Ошибку исполнения возвращаем МОДЕЛИ как результат (строка-JSON с полем error),
  а не бросаем пользователю: модель прочитает и переформулирует вызов или вежливо переспросит.
- Аргументы — недоверенный JSON от модели: проверять перед исполнением (typeof, белый список).
- Лимит раундов цикла (3–5) — первый guardrail против бесконечного вызова.
- Пустой результат поиска — тоже результат: честная строка «ничего не найдено»
  вместо выдумки.
- Описания функций пересылаются в каждом запросе (API без состояния). Их вес мал
  относительно истории, но: не дублировать общие правила (одно место — system prompt).
- system + functions — стабильный префикс запроса → кандидат на префиксный кеш
  (в `usage` есть `precached_prompt_tokens`). Держать их в начале и в стабильном порядке.
- Практика: в последнем чанке стрима есть `usage.prompt_tokens` — логировать и смотреть,
  как растёт вес истории.

## Где живёт что

- Определения функций и их исполнение — на сервере (ключи внешних API, файлы, БД).
- Исполнение — по белому списку: клиент шлёт только {name, args}, вызвать можно
  только зарегистрированный инструмент.
- Цикл: в нашем проекте — на клиенте (сервер остаётся «глухой трубой», история на клиенте).
  Сервер-агент (сам парсит SSE, клиент видит один стрим) — вариант для FastAPI/RAG-фазы.
