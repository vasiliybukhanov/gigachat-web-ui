# Стриминг SSE: как ответ модели течёт в браузер

Стриминг — не «загрузка файла по кусочкам», а конвейер: модель генерирует токены по одному,
каждый готовый кусок тут же уезжает по сети. Всё, что мы делаем, — перекладываем байты
из одной трубы в другую и разбираем события.

## Механика потока

- `stream: true` в запросе → сервер отвечает `content-type: text/event-stream`.
- Тело состоит из событий: строки `data: {...}`, разделитель — пустая строка (`\n\n`).
- `await fetch()` разрешается **после заголовков**, тело ещё не готово.
  `response.body` — ReadableStream: живая ручка к открытому TCP-соединению, а не «тело целиком».
- `await reader.read()` ждёт очередную порцию из сети (await висит, если данных нет — цикл спит).
  Один `read()` возвращает чанк TCP: может быть несколько событий сразу или полсобытия.
- Скорость потока задаёт модель. Ручной цикл read→write ничего не тормозит:
  тот же цикл внутри Nitro крутится при `return upstream.body`, только спрятанный.

## Парсер на клиенте (TextDecoder + буфер)

```ts
const decoder = new TextDecoder()
let buffer = ''
// в цикле чтения:
buffer += decoder.decode(value, { stream: true }) // stream: true — не резать многобайтовые символы
const events = buffer.split('\n\n')
buffer = events.pop()!                            // хвост — недокачанное событие, ждём продолжения
for (const e of events) {
  const payload = e.replace(/^data: /, '')
  if (payload === '[DONE]') break                 // ← ДО JSON.parse: parse('[DONE]') бросит исключение
  const chunk = JSON.parse(payload)
  const delta = chunk?.choices?.[0]?.delta?.content
  if (delta) reply.content += delta
  if (chunk?.choices?.[0]?.finish_reason) finished = true
}
```

- Буфер нужен, потому что границы TCP-чанков не совпадают с границами SSE-событий.
- `{ stream: true }` у TextDecoder — русские буквы (многобайтовые) могут прийти порезанными пополам.

## Дельты и finish_reason

- Обычный чанк: непустая `delta.content` и `finish_reason: null` — это 99% потока.
- `finish_reason` заполняется один раз, в последнем чанке (`"stop"`).
- Последний кусок текста может прийти **вместе** с finish_reason → порядок в обработчике:
  сначала дописать дельту, потом выходить из цикла. Иначе потеряем финальное слово.
- У GigaChat в промежуточных чанках поля `finish_reason` может вообще не быть
  (undefined, а не null) — optional chaining покрывает оба случая.
- После финального чанка возможен хвостовой с пустым `choices` и `usage` — пропускается сам.

## Обработка ошибок: две фазы сервера

- Фаза А (до отправки заголовков): можно вернуть честный HTTP-ответ —
  `throw createError({ statusCode, message })`, Nitro оформит JSON. Заголовки ещё можно менять.
- Фаза Б (после `setHeader('content-type', 'text/event-stream')`): статус 200 уже отдан,
  сменить его нельзя — ошибка передаётся только событием внутри стрима:
  `res.write('data: {"status":502,"message":"..."}\n\n')` + `res.end()`.
- Формат ошибки GigaChat — плоский JSON: `{"status": 400, "message": "..."}` (число + строка,
  без обёртки `error`). Сервер переиспользует его же для своих ошибок посреди стрима —
  один клиентский type guard ловит и то, и другое.

## Почему ручной цикл, а не `return upstream.body`

Nitro сам перекачивает ReadableStream — работает, но без контроля. Ручной цикл даёт:

1. ошибку апстрима можно сообщить клиенту событием внутри стрима (иначе — молча обрезанный текст);
2. уборку в `finally`: `await reader.cancel()` (отпустить апстрим) + `res.end()` (закрыть клиента)
   при любом исходе: успех, обрыв клиента, сбой upstream;
3. место для логов.

- Клиент ушёл («Стоп», закрытая вкладка) → `event.node.res.on('close', ...)` → `reader.cancel()`.
  `finally` срабатывает и после нормального завершения → двойной `end()` защищаем проверкой
  `if (!res.writableEnded)`.
- Backpressure: если клиент медленнее модели, `write` буферизует в памяти. Для чата неважно;
  общее решение — `if (!res.write(v)) await once(res, 'drain')`.

## Клиентская остановка

AbortController: `fetch(url, { signal: controller.signal })`, кнопка «Стоп» →
`controller.abort()` → соединение закрыто, сервер получает `close`.
